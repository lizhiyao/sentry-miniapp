# SDK 包体积审查

本记录保留 2026-10-12 的发布包归因和优化构建结果。发布包数据来自 npm 的 v1.20.4／v2.0.0，优化比较以 master `b38f7e1` 为基线，使用同一套锁定依赖和 Node 24.21.0 构建。优化构建的数据不代表已经发布的新版本。

## 发布包与运行文件

两个 npm tarball 均通过 registry 提供的 SHA-512 integrity 校验。npm 解包总量分别为 2,894,774 与 6,502,938 字节，包含三种 JS 格式、Source Map、类型和工具；约 91% 的新增解包字节来自 Source Map。

实际 CommonJS 文件分别为 170,479 与 264,137 字节。按 Source Map 的生成位置做近似归因，新增约 91.5 KiB 分为：兼容代码 41.3 KiB、SDK 实现 27.5 KiB、Core 17.9 KiB，其余构建辅助及声明约 4.7 KiB。归因只用于定位成本，不是独立模块的可删除体积。关闭运行时功能或保留已有宿主 API，不会自动移除已经内联的代码。

## 优化方式与边界

构建插件共享 core-js／core-js-pure 的基础模块，要求源码完全一致，且每个静态 require 的完整闭包都满足同一条件。两种模式的 export、path、共享存储、模式标记保持独立；hidden-keys、iterators、uid 与 is-forced 等独立可变状态不参与共享，间接依赖它们的模块也排除。动态或外部 require 不参与共享。插件锁定已审查的 3.50.0，依赖升级时必须重审这些边界，不能仅修改版本守卫。

ESM 输出启用 Oxc 的紧凑 codegen，并继续保留消费端 tree-shaking 使用的 PURE 注释。Core 协议、公共 API、宿主回退、初始化时序、许可证和 Source Map 内容均继续保留。构建没有新增压缩器依赖，也没有扩展已有的运行时依赖补丁。

| 实际文件 | 优化前原始字节 | 优化后原始字节 | 变化 | 优化前 gzip | 优化后 gzip |
| --- | ---: | ---: | ---: | ---: | ---: |
| CommonJS | 264,466 | 258,764 | −2.2% | 85,223 | 84,545 |
| ESM | 350,882 | 262,471 | −25.2% | 96,202 | 84,759 |
| UMD | 264,295 | 258,593 | −2.2% | 85,294 | 84,620 |

小程序专用 CommonJS bundle 为 258,760 字节，与标准 CommonJS 的差别来自文件名。ESM 的大幅下降包含格式空白的压缩，不能直接承诺业务小程序也减少 25%。使用同一 Rolldown 将 `init` 和 `captureException` 接入代码再次打包，产物从 245,519 降到 238,970 字节，约减少 2.7%；这是固定接入探针，不代表任意 Taro／uni-app 应用。

更换压缩器对已有 CommonJS 的试验收益不足 1 KiB，未引入额外依赖。仍存在的标准能力补齐与 SDK 生命周期成本需要分别评估，不通过删除跨端回退或关闭已有公共能力降低本轮数字。

## 验证与持续预算

适用检查包括 lint、typecheck、1297 个既有单测、标准构建／publint，以及实际安装包在七个平台 × 15 种宿主能力模拟中的 CJS／ESM 消费、UMD、类型与生命周期行为。小程序独立 bundle 验证实际加载和业务异常的原始源码映射。这里的宿主能力模拟不是七个平台的设备测试。

`check:bundle-size` 检查原始 JS 字节并报告 Node gzip 默认压缩结果，预算包含内联声明：ESM 260 KiB，CommonJS／UMD／小程序独立 bundle 255 KiB。标准构建和小程序构建都会执行，CI 的现有构建任务会阻止超限；Source Map 和类型不计入运行 JS 预算。

复核命令：

```bash
yarn run build
yarn run build:miniapp
yarn run check:bundle-size
```

依赖升级或新增能力导致超限时，在同一 PR 解释成本及验证结果，再决定是否调整预算。实际项目接入以平台包分析为准，分包建议见[主包体积优化](../website/guide/bundle-size.md)。

## 第二轮：移除可选集成的模块求值副作用

以 `fb99162` 为基线，移除内部集成 class 的静态 `id`，实例 `name` 保留原有名称。公共 API 继续只提供 factory，没有修改默认集成、启用条件或回退范围。静态字段在 ES2015 构建中降为 class 外部赋值，导致未引用的可选集成仍被保留；删除这层冗余可让消费端裁剪对应实现。

同一 Rolldown 基础接入探针从 238,915 降到 233,298 字节，减少 5,617 字节（2.4%）。完整 CommonJS 仅从 258,764 降到 258,501 字节，完整 ESM 从 262,471 降到 262,208 字节。此处收益主要发生在消费端按需打包，不能把它当作独立小程序 CommonJS 的同等减重。

实际安装包检查新增两个消费端边界：基础项目移除未使用的 Performance API／HTTP 上下文集成；显式启用 Performance API 的项目保留 observer 安装及 dispose 清理。两者运行真实 Core 异常发送和 flush，并执行消费端字节预算。探针自身的断言、模拟宿主和异步驱动也计入数字。

进一步试验没有并入生产构建：折叠 core-js 模式标记只减少约 115 字节；扩展共享状态边界收益不足 2 KiB；改用第二套 CommonJS 编译管道收益约 2 KiB 且 gzip 变大。去掉 Core 调试代码能省约 7 KiB，但会改变现有 `debug` 行为。改写标准方法安装或假设更多原生能力也会增加维护／兼容成本，未仅为压低数字引入。

## 精简入口评估与撤回

[PR #521](https://github.com/lizhiyao/sentry-miniapp/pull/521) 曾实现未发布的 `sentry-miniapp/lite`，由应用提供标准运行时能力。同一构建中，完整 CommonJS 依赖闭包为 259,504 字节，精简闭包为 221,406 字节，减少约 37.2 KiB；带运行断言的基础 ESM 消费探针分别为 235,699 与 193,986 字节。但应用为此补齐同一组标准能力的探针为 243,125 字节，反而更大。收益取决于应用已经具备所需能力，不能承诺所有项目都减重；完整实现和验证证据保留在该 PR。

该方案在发布前撤回。目前没有可复现的真实项目需求支撑第二入口带来的能力判断、加载顺序和多入口混用维护成本。项目保持单一公共入口，由 SDK 补齐所需标准能力；npm 的 ESM、CommonJS 和 UMD 继续各自生成独立文件，不保留精简导出、启动检查或共享 runtime 的拆分构建。

前两轮兼容辅助模块共享、ESM 压缩和可选集成按需裁剪继续保留，体积预算不变。后续优先根据真实应用的最终包分析定位成本；重新引入另一种入口前，须先有明确的目标宿主、已提供能力及净减重证据。
